# Project brief

Written from the repository before a frame was cut. Where documentation and code
disagreed, the code won and the disagreement is recorded at the bottom.

---

**PROJECT**
PACT — merchant-side authority reading for agentic commerce. One FastAPI process
behind one port (`deploy/app.py`) mounting four ASGI apps — gate, merchant,
demo, webhooks — with a React console served from `/`.

**PROBLEM**
Agentic commerce standardised how an AI agent *pays*. Nothing in the payment
path carries what the agent is *allowed* to spend, so a merchant quoting to an
agent is quoting blind. It upsells into limits it cannot see, and the buyer's
spending control — when there is one — usually lives inside the agent, where a
compromised agent simply does not run it.

**TARGET USERS**
The merchant integrating an agent channel (the primary buyer of this system);
the person delegating spend to an agent, who needs a control that is real; and
the agent developer, who wants refusals with codes rather than prose.

**SOLUTION**
A signed delegation the buyer's agent carries, a gate that decides on authority
alone, and a merchant that reads *remaining* authority before it prices. Because
the merchant can see what is left, every offer it makes is one the gate will
approve — which turns a spending limit from friction into a conversion
instrument.

**CORE FEATURES**
Mandate signing on the buyer's device (Ed25519 + RFC 8785 JCS); the headroom
envelope; an eight-check authority gate with machine-readable reason codes; a
reservation ledger; a headroom-aware upsell; a compensating saga with an
alternative the buyer must sign; a firewall surface that replays any decision
check by check; six scripted demo beats.

**TECH STACK**
Python 3.12, FastAPI, SQLite (WAL, `BEGIN IMMEDIATE`), httpx, Ed25519 via
`contracts/crypto.py`; React 18 + Vite + TypeScript, `@noble/ed25519` in the
browser; Docker, GHCR, Render; pytest (190 tests), vitest (55), Playwright.

**ARCHITECTURE**
`human device → agent → merchant → gate → ledger`, with the merchant reading a
headroom envelope from the gate *before* it quotes, and only an ALLOW reaching
`rails/`. `core/` is rail-agnostic and imports nothing from `rails/`;
`tests/test_invariants.py` enforces that with an AST walk, plus a second test
that forbids a vendor name on any executable line in `core/`.

**KEY DIFFERENTIATORS**
1. Authority is read *forward*, before the offer, not enforced afterwards.
2. Ceilings are reserved inside the transaction that writes the row, not counted.
3. The control is server side; the agent never holds the key.
4. The envelope discloses what is left and nothing else.
5. Refusals are typed reason codes, and an ablation matrix shows each check
   earning its place.

**PRIMARY USER JOURNEY**
Grant authority on the device → the agent states intent → the merchant prices
and reads headroom → the gate decides → settlement → an approvable add-on →
(when fulfilment fails) refund, budget release, and a replacement the buyer
signs.

**DEMO SCENARIO**
A single continuous take against a cold local instance: grant and sign, type
"restock office supplies for the month", accept the add-on the merchant offered
against remaining authority, then beats 1, 3, 4 and 5 and the firewall replay.
Beat 3 is included *because it fails* — that contrast is the pitch.

**TECHNICAL HIGHLIGHTS**
The atomic-versus-naive ledger comparison kept in the tree; the AST-enforced
rail boundary; the field-set test on the headroom envelope; the compensating
saga that parks in `NEEDS_ATTENTION` rather than swallowing a failed refund;
browser/server signature parity verified at console boot.

**MEASURABLE IMPACT** (all from `eval/results/results.md`, generated by `sim/run.py`)
Four arms × 200 sessions × 3 seeds. PACT nets ₹1,64,688 per 100 sessions against
a naive client-side cap's ₹1,31,517, with a 0.0% false block rate against that
cap's 27.8%, and ₹0 lost to adversarial traffic at every rate swept.

**LIMITATIONS**
The Razorpay client has never run against the live API (no test keys existed in
the build environment); arm A is modelled, not simulated; the 8% adversarial
rate is an assumption, swept across six points; below ≈18% adversarial traffic an
ungated channel still nets more under this loss model; two attack variants report
`N/A` because they target an auditor that is not running; the app needs a
persistent process, so it is not serverless-deployable as it stands.

**FUTURE SCOPE**
A live-rail run against real test keys; the auditor enabled so the two `N/A`
variants become passes; a second rail to exercise the rail-agnostic boundary
under real conditions; and multi-instance operation, which today is blocked by
the SQLite write lock the ledger depends on.

## Findings from production

Two things surfaced while filming, both worth acting on independently of the video.

**The console's upsell attach tile did not count what it appeared to count.**
**Fixed 2026-09-09.** `merchant/upsell.py` increments `offers_made` whenever the
merchant suggests add-ons, but `record_acceptance()` had exactly one caller —
`POST /v1/orders/{id}/accept_alternative`, the *rollback recovery* path. An
add-on accepted in the normal checkout flow is re-quoted into the order and
settles, and never incremented `offers_accepted`. So the tile read "0 of 7
offers accepted · 0%" on a run where an add-on had in fact been accepted and was
visible in the order line.

A re-quote now names the quote it replaces, and `record_requote()` decides what
counts: a SKU has to be new to the basket *and* one the engine actually offered
against that quote. Beats 1 and 2 against a cold instance put the tile at 1 of
3, 33.3%, agreeing with the beat's own `upsell_accepted`.

The film was cut around the checkout surface before the fix, where acceptance is
visible as a state change (`Add` → `added`) rather than as a counter. That cut
stands — it is the better shot, because a person performing the acceptance is
the point — and the merchant board behind it now tells the truth as well.

**A stale headroom poll after a reset.** The first take logged one 404:
`GET /api/gate/v1/mandates/{id}/headroom` for a mandate the reset had just
cleared. It is harmless and happened before the first mark, but it is the only
console error either take produced; the second take produced none.
